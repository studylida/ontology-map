# 기사 전체 최소 추출 진단 결과

## 1. 확인하려던 것

앞선 목적 표집 비교에서는 원문 보존 문구가 다음 후보로 남았다. 이번에는 사람이 focus 문장을 미리 고르지 않고 기사 전체에서 지식 후보를 만들 때도 그 방향이 유지되는지, 그리고 진단 필드가 많은 출력과 최소 출력 중 어느 형태가 실행 가능한지 확인했다.

두 조건은 같은 공식 한국어 기사 4건, 같은 원문 보존 prompt, 같은 모델 `qwen3.7-flash-2026-07-15`, temperature 0, thinking·streaming 비활성, strict JSON Schema를 사용했다. 풍부한 조건은 `statement`, `modality`, `critical_elements`, `main_source_ids`, `context_source_ids`를, 최소 조건은 `statement`, `modality`, `source_ids`만 반환하게 했다. 일반 코드는 원문 ID, 정확한 slice·offset·hash와 출력 구조만 검사했으며 의미를 자동 보충하거나 수정하지 않았다.

필수 사실 21개, modality, 충분한 근거 조합과 분리 기준은 출력 확인 전에 동결했다. 각 조건은 기사별 두 번 실행하도록 계획했으며 repair·재시도·fallback은 허용하지 않았다.

## 2. 3,000-token 비교는 성립하지 않았다

| 항목 | 결과 |
| --- | ---: |
| 계획 호출 | 16 |
| 계약 성공 | 4 |
| 길이 계약 오류 | 12 |
| 풍부한 조건 성공 | 0/8 |
| 최소 조건 성공 | 4/8 |
| 실제 추정 비용 | `$0.00747342` |

실패 12회는 모두 `finish_reason=length`, completion 3,000 tokens, 로컬 오류 `INCOMPLETE_OR_REFUSAL`이었다. 풍부한 출력은 네 기사 모두 두 번씩 잘렸고, 최소 출력도 긴 M01·M02에서 잘렸다. 최소 출력의 M03·M04만 통과했다. strict JSON Schema 자체가 전부 거부된 것은 아니지만, 비교 가능한 기사 3건이라는 사전 조건을 충족하지 못해 의미 점수를 내지 않았다.

## 3. 최소 출력 6,000-token 후속

앞서 합의한 “출력 상한이 실제 문제가 되면 1.5~2배 안에서 조정한다”는 경계에 따라 별도 manifest를 동결하고 최소 출력만 6,000 tokens로 실행했다. 원문, gold, prompt, schema, 모델과 나머지 설정은 바꾸지 않았다. 출력 상한 선택에 같은 자료를 사용했으므로 이 라운드는 독립 평가가 아니라 개발 근거다.

| 항목 | 결과 |
| --- | ---: |
| 호출 계약 성공 | 8/8 |
| completion tokens 범위 | 1,932~4,564 |
| 생성 Claim | 384, 호출당 평균 48 |
| unresolved 묶음 | 0 |
| 필수 사실 PASS | 20/42 |
| 필수 사실 PARTIAL | 22/42 |
| Claim SUPPORTED | 302/384 |
| Claim UNSUPPORTED | 74/384, 19.27% |
| Claim OVERMERGED | 8/384 |
| 실제 추정 비용 | `$0.00425141` |

사전 유지 기준은 8/8 계약 성공, 필수 사실 PASS 30/42 이상, 비지원 Claim 5% 이하, 두 반복에서 되풀이된 중대 오류 0건이었다. 계약만 통과했고 나머지 기준을 충족하지 못해 `REJECT_MINIMAL_6K_QUALITY_CANDIDATE`로 판정했다.

## 4. 남은 오류와 의미

| 오류 | 필수 사실 판정 수 | 해석 |
| --- | ---: | --- |
| 발언 귀속·modality 불일치 | 7 | 회사 수치를 설명한 발언자 누락, 협력 계획과 견해를 FACT로 분류하는 문제가 반복됐다. |
| 필수 의미 누락 | 6 | 완료된 양산을 “양산을 위한 성과”로 약화하고 재무 건전성과 주주환원 사이의 관계를 잃었다. |
| 연결 근거 부족 | 6 | 생략 주체, 지시어 또는 사양 행의 제품을 문장에는 복원했지만 필요한 선행 ID를 연결하지 않았다. |
| 원문 비지원·변경 | 1 | 메모리 사업 계획을 삼성전자 전체 계획으로 넓힌 사례가 있었다. |
| 사실 병합 | 3 | 서로 다른 세 아키텍처와 용도를 한 Claim에 묶었다. |

필수 사실에서는 M01-F01, M02-F04, M03-F04, M04-F04~F06에 같은 중대 오류가 두 반복 모두 남았다. 전체 Claim 검토에서도 M02의 부문 제목, M03의 `이를 통해`·`그 이후`, M04의 사양 행과 대명사처럼 앞 문맥 없이는 주체를 확인할 수 없는 경우가 집중적으로 실패했다.

이는 문장을 원문에 가깝게 쓰는 것만으로는 충분하지 않다는 뜻이다. 모델은 전체 기사를 읽고 올바른 주체를 문장에 넣기도 했지만, 그 주체를 증명하는 선행 `source_id`는 자주 빼먹었다. 최종 DB에는 문장뿐 아니라 정확한 Observation 연결이 필요하므로, 문장이 사실처럼 보여도 연결 근거가 부족하면 자동 승격할 수 없다.

## 5. 사전 점수 밖에서 발견한 selection 결함

M01 두 반복에서 prompt가 명시적으로 제외한 HBM·QLC·PIM 등 일반 정의를 각각 10개씩 추출했다. 같은 14.3조 원 주주환원 사실을 제목과 본문에서 중복 추출했고, M03에서는 같은 전시 행위를 겹치게 만들었다. 이 결함은 출력을 본 뒤 분류했으므로 사전 성공 기준을 바꾸거나 기존 점수에 소급 합산하지 않고 `review.json.selection_issues`에 별도로 남겼다.

384개라는 개수 자체가 잘못은 아니다. M02의 사업 부문 계획과 M04의 제품 사양처럼 그래프에 유용한 구체적 사실도 많다. 다만 “모든 구체적 사실을 빠짐없이”라는 지침과 “일반 정의·안내를 제외”한다는 지침 사이에서 선택 경계가 안정적으로 지켜지지 않았고, 호출 크기와 후속 검증 부담도 커졌다.

## 6. 동결 gold의 민감도

M04-F06의 동결 근거는 `s19+s20`이지만, `s20` 자체에도 와일드캣 레이크와 17 TOPS NPU가 모두 명시돼 있다. 문장·표 행 단위를 허용한다는 정책에서는 `s20`만으로 충분하다고 볼 수 있다. 사전 원장은 그대로 보존했으며 공식 점수도 바꾸지 않았다. 이 두 판정을 PASS로 바꾸는 민감도에서도 22/42에 그치고 다른 반복 오류와 19.27% 비지원 Claim이 남아 후보 기각은 바뀌지 않는다.

이 사례는 다음 gold에서 “선행 문맥이 실제로 필요한 경우”와 “같은 단위가 이미 자기완결적인 경우”를 더 엄격히 구분해야 함을 보여준다.

## 7. 비용과 보안

두 라운드의 새 비용은 `$0.01172483`이고, #139의 누적 예약·추정 비용은 `$0.88211297 / $1.00`이다. 실패 호출도 비용에 포함했고 자동 재호출은 하지 않았다. 기존 WSL 키 파일은 시험 프로세스에서만 읽었으며 키를 출력·게시·삭제하지 않았다.

## 8. 제품 계약에 미치는 영향

이번 결과로 새 DB table, column, task kind, publication pointer가 필요하다는 증거는 없다. 기사 전체, 후보 묶음과 원문 구조 정보는 runtime에 두고, 검증을 통과한 Claim과 정확한 Observation 연결만 기존 schema에 저장할 수 있다. 원응답·중간 후보·수동 판정 원장을 제품 DB에 넣지 않는다.

풍부한 출력은 3,000-token 조건에서 실행 가능성을 확보하지 못했고, 최소 출력은 계약은 안정화했지만 근거 연결과 선택 품질이 부족했다. 따라서 지금 `critical_elements`나 별도 검증 Agent를 제품 계약으로 확정하지 않는다.

## 9. 다음 권고

다음 유료 비교 전에 일반 코드만으로 원문 구조를 보존하는 입력 투영을 먼저 만든다. 현재 모델 입력은 `source_id`, offset과 text만 보내며, 수집 단계에 이미 있는 `paragraph_id`를 버린다. 문단 경계와 HTML에서 검증 가능하게 얻은 section·list·table 소속을 runtime 정보로 전달하면, 모델이 지시어·생략 주체·사양 행의 실제 선행 근거를 고를 수 있는지 한 조건만 바꿔 비교할 수 있다.

단순 앞뒤 인접 ID 묶음은 이전 시험에서 반복 개선을 만들지 못했으므로 되살리지 않는다. gold를 보고 정답 ID를 넣거나, 모델이 빠뜨린 근거를 코드가 의미적으로 추측해 보충하지 않는다. 구조 정보가 원문 HTML에서 결정적으로 복원되지 않는 자료는 추측하지 않고 적용 불가로 기록한다.

이 입력 후보를 만들기 전에 공개 HTML 네 건에서 문단·section·목록·표 구조가 얼마나 보존되는지 비용 없는 감사를 먼저 수행한다. 구조가 충분할 때만 새 원문·사건 계열 자료로 최소 출력 A/B를 계획하고, selection 과잉·연결 근거·필수 의미를 모두 사전에 평가 항목으로 고정한다.
