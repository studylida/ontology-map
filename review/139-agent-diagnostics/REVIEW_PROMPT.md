# ontology-map Agent 개선 방향 독립 검토 요청

당신은 ontology-map의 한국어 지식 추출·검증 방식을 독립적으로 검토하는 연구·설계 검토자다. 기존 에이전트의 제안을 승인하는 것이 목적이 아니다. 문제 정의와 실험 전략부터 반박하고, 현재 접근을 유지·축소·교체할지 판단해 달라. 사용자는 다음 업무일에 이 결과를 읽고 후속 실험을 결정하려 한다. 이번에는 질문만 돌려주지 말고, 자료로 판단 가능한 사항에 대한 추천과 이유를 먼저 완성해 달라.

## 1. 자료와 확인 범위

이 프롬프트를 전달한 메시지의 검토 branch와 commit을 기준으로 다음 자료를 읽어 달라. 같은 branch가 나중에 변경되면 기준 commit의 자료와 섞지 말라.

- [README.md](README.md): 검토 패킷의 목적, 기준, 포함·제외 자료와 Issue 연결.
- [EXPERIMENTS.md](EXPERIMENTS.md): 수행 과정, 결과, 비용과 보류 상태의 요약.
- [CASES.md](CASES.md): 문제를 설명하기 위해 재구성·요약한 사례. 실제 요청이나 원응답의 완전한 사본이 아니다.
- [prompts-and-schemas.json](prompts-and-schemas.json): 실제 시험에 사용한 prompt와 JSON schema.
- [results-metadata.json](results-metadata.json): 마지막 49회 호출의 식별자·비용·구조 검사 상태·해시와 판정·근거 ID 발췌. 원문·Claim 문장·이유·전체 응답은 들어 있지 않다.
- [evaluation-summary.json](evaluation-summary.json): 마지막 시험의 집계와 평가 요약. 평가자의 의미 판정을 독립적으로 재검증한 자료는 아니다.
- `snapshots/`: 실제 시험 계약·검증 코드의 읽기 전용 텍스트. 실행 환경과 원시자료가 없어 완전 재현 패키지가 아니다.

제품과 데이터 계약이 필요한 판단은 저장소의 [문서 안내](../../docs/README.md), [논리 스키마](../../docs/data/logical-schema.md), [물리 스키마](../../docs/data/physical-schema.md)와 연결된 Issue를 확인하라. 현재 병합된 계약, 승인된 변경안, 시험용 가설을 구분하라. 검토 branch의 자료는 정식 제품 계약이 아니다.

원시 입력·출력이 없는 경우 요약의 의미 판정을 독립 검증했다고 주장하지 말라. 해시와 구조 검사는 내용의 의미 정확성을 증명하지 않는다. 읽지 못한 자료, 확인 불가능한 주장과 필요한 추가 증거를 명시하라. 재구성 사례에 직접적인 측정값을 붙여 새 실험 결과처럼 쓰지 말라.

## 2. 해결하려던 문제와 유지할 원칙

목표는 공개 한국어 자료에서 사용자가 탐색할 지식그래프를 만들 때 중요한 사실과 조건을 잃거나 바꾸지 않는 것이다. 주체 누락, 서로 다른 대상의 잘못된 묶음, 지시어 해소에 필요한 선행 근거 누락, 시점·수량·부정·계획·발언 귀속의 손실을 줄이려 했다. 최근 시험은 주로 추출 결과를 검사하는 진단 도구에 집중했다. 이 진단 역할이 각각 제품 Agent로 승인된 것은 아니다.

- 법 제정 추진과 지원 계획은 삭제할 정보가 아니라 그 상태를 보존할 정보다. 추진 중인 법을 이미 제정된 법처럼, 계획을 현재 시행 사실처럼 쓰면 안 된다.
- 발언자와 중요한 평가·기술 적용 대상은 보존한다. 발언자의 평가를 객관적으로 입증된 사실로 바꾸면 안 된다. 회사의 공식 입장일 가능성도 있으므로 인물 발언을 회사와 무관하다고 일괄 처리하지 않는다.
- 서로 다른 제품의 독립 사실은 분리하고, 실제 공동 행위와 그 참여자는 함께 보존한다. 어려운 사실·조건을 버리거나 판정 불가를 통과로 계산해 점수를 높이지 않는다.
- 문장 전체와 표 행 전체는 허용된 근거 단위다. 같은 단위에 부가 절이나 다른 셀이 있다는 이유만으로 실패시키지 않는다. 이것이 문단 전체의 과도한 인용 문제를 해결했다는 뜻은 아니다.
- 일반 코드가 원문·후보 조회, 실행 순서, 검증과 최종 저장을 맡는다. Agent는 주어진 범위에서 생성·판정한다. 모델의 승인 신호가 코드 검사를 대체하지 않는다.
- 기존 frozen schema를 먼저 재사용한다. 실행 중 후보·판정·분해 목록이 있다는 이유만으로 영속 저장이나 새 task kind가 필요한 것은 아니다. 사람의 상시 판정을 전제로 해결하지 않는다.

이 원칙 내부에 모호함이나 모순이 있다면 실제 사례로 지적하고 대안을 제시하라. 다만 원칙을 조용히 바꿔 정답률을 높이거나 새 제품 계약으로 확정하지 말라.

## 3. 결과를 해석할 때 주의할 사실

직전 74회 시험에서는 별도 Composer의 추가 의미 개선이 확인되지 않았다. 원문에서 필수 사실을 찾고 Claim에 대응시키는 Preservation은 일부 성과를 보였지만, 검사기가 적은 사실 자체에 선행 근거가 빠지는 문제가 남았다. 여러 검사를 함께 수행하는 Fidelity는 일부 근거 누락과 제품 묶음을 놓쳤다.

마지막 49회에서는 근거 검사에 전체 기사 또는 실제 연결된 원문만 제공하는 조건을 비교했다. 연결 원문 격리는 선행 근거가 빠진 두 Claim의 탐지에 도움이 됐다. 독립 사실 목록을 출력하게 한 비교에서는 제품 묶음을 잡았지만 공동 개발자 누락을 사실 분리 오류로 오판했다. 한 차례 수정 뒤에도 문제가 남아 합의한 중단 조건에 따라 확대·반복을 멈췄다.

최종 근거 검사 후보의 판정은 25개 중 23개가 맞았고, 이유·근거까지 포함하면 22개가 맞았다. 실제 근거 오류 7개 중 5개를 탐지했고 정상 18개는 모두 통과했다. 동일 Claim·선택 근거 23개만 이전과 비교하면 20/23에서 22/23으로 변했지만, 여러 설정이 달라 단일 변경의 인과 효과로 해석할 수 없다. 새 발언 귀속 후보는 그 비교에서 제외됐다.

이 자료는 조정에 사용한 7개 개발 지점과 정상·오류 대조쌍이며, A4는 합성 자료다. 긴 원문을 제공했어도 검사 지점은 시험자가 지정했다. 독립 기사 14편의 성능이나 원문 전체에서 자율적으로 누락을 발견한 성능으로 해석하지 말라. 전송·출력 구조 검사 통과도 의미 판정 통과가 아니다. 평가 기준을 바꿔 경고가 타당해진 효과와 모델을 개선한 효과는 별도로 기록했다.

기존 Preservation 사실의 추가 근거 검사와 새 긴 기사 독립 평가는 보류 상태다. 마지막 중단은 예산 소진이 아니라 시험의 실패 조건 때문이었다. 작은 개발 자료의 통과를 요구하는 이 진행 규칙 자체도 검토할 수 있지만, 이번 검토가 실행 재개 승인은 아니다.

## 4. 핵심 검토 질문

### 문제 정의와 평가

1. 추출 품질을 개선하려던 작업이 검증기의 개발 정답률을 올리는 작업으로 바뀌었는가? 현재 진단 결과가 실제 추출·저장·사용자 탐색 품질을 높이는 경로를 설명하고, 연결이 끊긴 부분을 지적하라. 추출기 개선과 검사기 개선 중 무엇을 먼저 해야 하는지 반대 근거까지 검토하라.
2. 필수 사실 선정, 원문 지원, 선택 근거 충분성, Claim 분리는 서로 다른 판단인데 현재 gold·prompt·집계가 이를 일관되게 구분하는가? 같은 사례가 여러 검사에서 실패해야 하는 경우와 한 검사만 담당해야 하는 경우를 제시하라. 모델 오류, 모호한 제품 기준, 평가자 해석 오류를 분리하라.
3. 같은 개발 지점을 반복 보고 모든 사례가 통과해야 독립 평가를 여는 규칙은 과적합을 유도하는가? 모델 입력에는 gold가 없더라도 prompt 조정, focus 지정, 후보 문체와 평가자의 선택에서 정보가 새어 들어갈 수 있는가? 기존 점수를 보존하면서 이를 확인할 방법과 진행 규칙의 대안을 제안하라.

### 남은 오류와 반증 가능한 원인

4. A3에서 회사 계획은 맞지만 발언자의 평가가 직접 사실로 변한 것을 놓쳤다. 중요한 절별로 검사를 나누면 도움이 되는가, 아니면 필요한 속성을 과도하게 설계하는가? 평가를 생략하거나 회사·인물의 관계를 일괄 처리하지 않고 두 가설을 가를 최소 대조를 제안하라.
5. A4의 “A와 B가 공동 개발한다”에서 “B가 개발한다”는 더 약한 참여 명제로는 지원되지만 공동성은 누락됐다. 이를 “B만 단독 개발한다”로 읽고 사실 분리까지 실패시키는 현상을 어떻게 설명하는가? 원문을 제거한 분리 검사, 역할 통합, 별도 분리 검사 제거도 비교하라. 원문을 줄이면 다른 오류를 놓칠 가능성도 검토하라.
6. A5에서 선택 원문 격리가 탐지에 도움이 됐지만, 검증기 자신이 적은 필수 사실의 근거도 빠졌다. 원문→필수 사실→Claim→연결 근거를 어떤 최소 방식으로 대응시켜야 하는가? 원문 누락 검사와 Claim의 지원 검사를 서로 대신 사용하지 않고, 모델이 연결하지 않은 근거로 빈틈을 메우는 것도 방지할 수 있는가?
7. A7에서는 표 머리글과 행이 있어도 한 제품의 제한 조건을 다른 제품으로 옮겼다. 표 구조를 일반 코드가 명시하는 방법, 제품별 입력을 분리하는 방법, 모델이 표를 직접 읽는 방법을 비교하라. 코드가 의미를 추측하지 않고 기존 원문 범위를 보존하는 경계는 어디인가? 이전 표 Selection 시험의 성공을 이번 Evidence 회귀 해결 근거로 재사용하지 말라.
8. 판정은 맞지만 실제 Claim에 없는 단어를 이유에서 인용한 사례는 무엇을 뜻하는가? 짧은 이유·근거 ID·직접 인용 중 무엇이 검증 가능성을 높이는지 검토하라. 이유나 reasoning이 실제 판단 원인의 충실한 설명이라고 가정하지 말고, 코드가 확인할 수 있는 조건과 의미 판단이 남는 부분을 구분하라.

### 더 단순한 구조와 다음 실험

9. 여러 진단 역할을 계속 나누는 방식, 추출 입력·출력을 구조화하고 일반 코드 검증을 중심에 두는 방식, 호출과 역할 수를 줄이는 방식 중 무엇이 적합한가? 최소 세 대안을 같은 기준으로 비교하라. 현재 제안과 다른 접근을 적어도 하나 포함하되, Agent·framework·schema부터 늘리지 말라.
10. 백엔드가 원문 ID·문자 범위·선택 근거 격리·표 열 대응·허용 참조·인용 일치를 맡으면 어디까지 해결되는가? 의미 판단과 영속 저장의 경계는 무엇인가? 시험용 진단 호출을 기존 `agent_attempt`에 일반 작업처럼 끼우거나 새 task kind로 확정하지 말고, 현재 계약으로 표현할 수 없는 사실이 있다면 위치와 이유부터 제시하라.
11. 전체 정답률 대신 오류 종류별 미탐·오탐, 필수 사실 보존, 근거 충분성, 호출 비용과 반복 안정성을 어떻게 함께 볼 것인가? 개발 자료의 작은 통과를 과장하지 않으면서 다음 단계로 진행할 수 있는 현실적인 기준을 제안하라. 실패 후보를 대량 제외해 지식량이 줄어드는 손실도 비용에 포함하라.

## 5. 원하는 산출물

1. 먼저 현재 방향에서 유지할 것·줄일 것·중단할 것·확인 불가능한 것을 요약하고, 가장 중요한 추천을 제시하라. 기존 추천에 동의한다면 독립적인 이유를 쓰고, 반대한다면 근거를 제시하라.
2. 핵심 사례별로 `관측 사실 / 가능한 원인 / 다른 설명 / 원인을 구분할 실험 / 성공·실패 기준 / 확인 한계` 표를 작성하라. 모델의 설명을 원인의 확정 증거로 사용하지 말라.
3. 최소 세 대안을 정확성·누락 위험·복잡도·호출 수·비용·기존 schema 영향으로 비교하고 하나를 추천하라. 비용은 가정과 산식을 밝히고 확인하지 않은 모델 가격을 사실로 쓰지 말라.
4. 다음 업무일에 검토할 우선 실험 세 개를 제시하라. 각 실험에서 입력·출력·모델 설정 중 무엇 하나를 바꾸는지, 무엇을 고정하는지, 두 결과가 각각 어느 가설을 지지하는지, 예상 호출 수와 중단 조건을 명시하라. 여러 변경이 함께 필요하면 비교를 어떻게 나눌지 설명하라.
5. 개발·회귀·독립 자료의 분리, 후보 고정 시점, 평가 변경 기록, 확대·중단 기준을 제안하라. 이전 실패와 기존 점수를 보존하고 실제 독립 평가를 조정 자료로 다시 쓰지 않는 방법을 포함하라.
6. 마지막에 사용자 결정이 필요한 사항과 추가 증거가 필요한 사항만 남겨라. 각각 왜 지금 결정해야 하는지 설명하고, 자료에서 확인 가능한 사실을 사용자에게 다시 묻지 말라.

## 6. 권한과 조사 제한

이번 요청은 읽기 전용 검토와 제안이다. 코드·정식 문서·DB·migration·metadata·fixture·의존성을 변경하거나, 모델을 호출하거나, 데이터를 적재하거나, Issue·branch·PR을 생성·수정·삭제하지 말라. 기존 보류 작업을 재개하거나 제품 Agent·새 schema·새 영속 저장 계약을 확정하지 말라. 키나 비공개 원문·전체 응답을 요구하거나 공개 서비스로 올리지 말라.

웹과 공개 GitHub는 읽기 전용으로 참고할 수 있다. 외부 사례를 사용한다면 공식 문서·논문·실제 구현을 구분하고 근거 URL, 확인한 버전이나 commit, 참고할 최소 부분과 우리 문제에 적용되지 않는 차이를 적어라. 제안의 반대 근거도 찾아라. 영어·다른 모델·다른 데이터에서의 성과를 한국어 Qwen의 성과로 바꾸어 설명하지 말라. 새로운 유료 서비스나 의존성 도입은 이번 검토의 실행 범위가 아니다.

당장 실행 가능한 개선안이 없더라도 괜찮다. 어느 가정이 검증되지 않았고 어떤 작은 실험이 결정을 바꿀 수 있는지 명확히 설명해 달라. 우리가 원하는 답을 맞히는 것보다, 잘못된 방향이라면 근거를 들어 멈추게 하는 것이 이 검토의 목적이다.
