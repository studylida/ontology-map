# ontology-map 원문 보존형 추출 비교 독립 검토 요청

당신은 ontology-map의 한국어 지식 추출 실험을 독립적으로 검토하는 연구·설계 검토자다. 이전 검토에서는 검증기를 계속 세분화하기보다 원문을 덜 변형하는 추출 경로를 먼저 비교하라고 추천했다. 그 추천에 따라 수행한 첫 비교 결과를 검토하고, 원문 보존 문구를 다음 후보로 유지할지와 다음 한 번의 최소 실험이 무엇이어야 하는지 판단해 달라. 기존 에이전트의 결론을 승인하는 것이 목적이 아니며, 근거가 약하면 중단하거나 다른 방향을 추천해도 된다.

## 1. 읽을 자료와 증거 경계

이 프롬프트를 전달한 메시지의 `docs/139-agent-review` branch와 commit을 기준으로 먼저 [README.md](README.md)를 읽고, 같은 폴더의 `REPORT.md`, `manifest.json`, `preserve-addendum.txt`, `gold.json`, `blind-review.json`, `blind-map.json`, `score.json`, `source-index.json`, `call-metadata.json`을 대조하라. 이전 단계의 맥락이 필요할 때만 상위 폴더의 `README.md`, `EXPERIMENTS.md`, `CASES.md`, `prompts-and-schemas.json`, `results-metadata.json`, `evaluation-summary.json`과 `snapshots/`를 읽어라.

제품 계약이 필요한 판단은 저장소의 `docs/data/logical-schema.md`, `docs/data/physical-schema.md`, `docs/data/schema-reference.md`, ADR-0005·0006과 Issue #124·#125·#127·#128·#139를 확인하라. 현재 병합된 계약, 승인된 Issue의 미래 계약, 시험용 runtime 형식과 이 branch의 검토 자료를 서로 구분하라.

기사 전문과 모델 원응답은 공개하지 않았다. `source-index.json`의 공식 URL을 읽을 수 있어도 공개되지 않은 모델 출력과 직접 대조할 수 없으므로, 128개 의미 판정을 독립 재채점했다고 주장하지 말라. `gold.json`은 사전 동결한 의미 요약이고 `blind-review.json`은 한 명의 수동 판정 원장이다. hash와 구조 검사는 내용의 의미 정확성을 증명하지 않는다. 확인 가능한 사실, 기록상 관측, 원인 가설과 확인 불가를 명시적으로 구분하라.

## 2. 비교 설계와 관측 결과

이번 비교의 유일한 의도된 변경은 동결된 R7 prompt에 `preserve-addendum.txt`를 추가한 것이다. 모델, temperature, thinking·streaming, 출력 상한, 기존 prompt·출력 형식, 기사, focus 원문 단위와 반복 횟수는 고정했다. 이전 개발 자료와 URL·문서 hash가 겹치지 않는 공식 한국어 기사 8건에서 기사별 2조건 × 2반복으로 총 32회 호출했고, 출력 전에 기사별 문장·표 행 4개의 필수 의미를 동결했다.

기존 조건의 엄격 통과는 27/64(42.2%), 원문 보존 조건은 37/64(57.8%)였다. 계약 실패를 제외한 통과율은 48.2%와 61.7%였고, 같은 원문 단위의 비계약 짝비교는 원문 보존 우세 11건, 기존 우세 1건, 동률 40건, 계약 실패로 제외 12건이었다. 반복 판정 일치는 79.2%와 89.3%였다.

총 32회 중 3회가 출력 계약에 실패했다. 두 번은 잘못된 key 또는 허용되지 않은 dimension이고 한 번은 3,000-token 출력 상한 도달이었다. 조건별 계약 성공 호출은 기존 14/16, 원문 보존 15/16이다. 어느 조건도 기사 한 번의 네 평가 단위를 모두 통과한 사례가 없었으며 두 조건 모두 0/16이다. 의미·근거 `FAIL`은 기존 9개, 원문 보존 10개여서 개선이 단순히 모든 오류를 줄였다는 결과도 아니다.

관측된 개선에는 계획·수요 조건, 개발 중 상태, 공개 범위, 공동 개발 목적·발언 modality, 선행 대상과 비교 제한의 보존이 포함된다. 남은 실패에는 지시어의 선행 대상 원문 누락, 여러 문장에 걸친 발언·계획의 뒤 절을 사용하면서 해당 원문 ID를 연결하지 않는 문제, 수치의 적용 조건과 발표 시점 누락이 포함된다. 회귀 1건은 전략적 협업 조건을 문장에서 빼고 원문 ID로만 남긴 경우다.

이번 8건은 목적 표집한 독립 원문·사건군 8개이며 128개는 조건과 반복을 포함한 평가 항목 수다. 이를 독립 표본 128개나 운영 성능으로 해석하지 말라. 이번 비용은 $0.01267030이고 이전 사용량·불명확 예약을 포함한 누적값은 $0.86442523이다.

## 3. 검토 질문

1. 의도된 변경이 실제로 원문 보존 문구 하나였다는 점, gold 동결 시점, 조건 가림, 요청 hash, 반복과 집계 분모가 공개 자료에서 일관되는지 감사하라. 확인할 수 없는 부분은 추정하지 말고 필요한 최소 증거를 적어라.
2. 계약 실패의 조건별 불균형과 같은 기사·원문 단위의 반복 의존성을 고려해도 `+15.6%p`, 비계약 짝비교 `11 대 1`, 반복 일치 개선이 원문 보존 문구를 다음 후보로 유지할 충분한 근거인지 판단하라. 탐색적 후보 선택과 제품 채택을 분리하고, 표본이 허용하지 않는 통계적 주장은 거부하라.
3. `gold.json`, `blind-review.json`과 `score.json`의 판정 기준과 계산을 감사하라. 특히 의미는 보존했지만 연결 원문이 부족한 경우, modality·발언 귀속이 틀린 경우, 일부 필수 조건만 남은 경우, 하나의 focus 문장에 대응한 gold가 뒤 문장까지 요구하는 경우가 일관되게 `PASS`·`PARTIAL`·`FAIL`로 분류됐는지 검토하라. 원문·원응답이 없어 판정 자체를 확인할 수 없다면 방법론상의 위험만 지적하라.
4. 두 조건 모두 완전한 기사 시도 0/16이고 원문 보존 조건의 의미·근거 `FAIL` 수가 줄지 않았다는 사실을 어떻게 해석해야 하는가? 평균 단위 통과율 개선이 사용자에게 쓸 수 있는 지식 묶음의 개선으로 이어지지 않은 이유와, 이를 다음 평가에서 측정하는 가장 단순한 방법을 제시하라.
5. 남은 병목을 `문장 재작성`, `원문 단위 선택`, `담화·지시어 묶음`, `근거 ID 연결`, `출력 schema 복잡도`, `엄격한 Structured Output 미사용`, `출력 상한`, `수동 평가 오차`로 나누고 근거 수준과 우선순위를 정하라. 서로 다른 원인을 한 번에 고치는 계획은 피하라.
6. 다음 단일축 후보로, 기존 문장·표 행 ID와 정확한 slice는 유지하되 발언·지시어가 이어지는 원문 단위를 runtime 입력에서 명시적으로 묶는 방식을 검토하라. 이 방식이 Observation 계약이나 DB schema를 바꾸지 않고 가능한지, 백엔드가 결정적으로 제공할 정보와 Agent가 의미적으로 판단할 부분을 구분하라. 문단 전체를 새 근거 단위로 바꾸거나 다른 원문을 몰래 보충하는 안은 추천하지 말라.
7. Flash의 엄격한 Structured Output 호환성 확인을 의미 품질 비교보다 먼저 할지, 병렬이 아닌 별도 소규모 시험으로 할지 판단하라. prompt 기반 JSON object에서 발생한 잘못된 key·허용되지 않은 dimension·길이 종료를 각각 같은 원인으로 묶지 말고, 호환성 시험이 의미 품질을 개선했다고 오해하지 않을 완료 기준을 제시하라.
8. 원문 보존 지침을 더 길게 만들거나 과거 오류별 예외를 계속 추가하는 대신, 삭제하거나 단순화할 기존 지침·필드가 있는지 검토하라. Selection·Composer·Preservation·Fidelity·Evidence·Atomicity를 각각 상시 제품 Agent로 만들거나 새 task kind·staging table·reasoning 저장을 추가하는 방향은 증거가 있을 때만 제안하라.
9. 이 8건을 회귀 자료로 전환한 뒤 사용할 새 독립 평가 자료를 어떻게 나눌지 제안하라. 분리 단위는 문장이나 Claim이 아니라 원문·사건·재게시 계열이어야 하며, 결과를 본 뒤 기준을 바꿔 같은 자료를 다시 독립 평가로 세지 않는 규칙을 포함하라.
10. 최종적으로 #139에서 한 번 더 수행할 가장 작은 비교와 #127에 넘길 수 있는 결정·넘기면 안 되는 결정을 구분하라. 제품 worker, 자동 저장, 새 schema와 운영 품질 승인은 이번 자료로 결정하지 말라.

## 4. 원하는 산출물

1. 첫머리에 `다음 후보 유지 / 추가 증거 전까지 보류 / 후보 폐기` 중 하나를 선택하고, 가장 강한 근거와 가장 강한 반대 근거를 각각 제시하라.
2. `직접 확인 / 기록상 관측 / 원인 가설 / 확인 불가` 표로 핵심 주장을 분류하고 각 항목에 파일 경로와 JSON field 또는 Markdown 절을 붙여라.
3. 기존·원문 보존 조건을 전체 항목, 계약 성공 항목, 짝비교, 기사·반복 단위로 나누어 해석하라. 128개를 독립 표본으로 계산하거나 계약 오류를 임의로 PASS·누락으로 바꾸지 말라.
4. 평가 설계의 결함이나 판정 원장의 불일치 가능성을 심각도순으로 적어라. 공개 자료만으로 의미 판정을 고칠 수 없다면 숫자를 새로 만들지 말고, 다음 시험 전에 고칠 절차만 제안하라.
5. 다음 실험 하나를 `가설 / 바꿀 한 조건 / 고정할 조건 / 자료 분리 / 호출 수 / 비용 상한 / 사전 gold / 성공·회귀·중단 기준 / 결과별 다음 결정` 형식으로 완성하라. 별도의 Structured Output 호환성 시험이 먼저 필요하다면 최대 호출 수와 성공 기준을 따로 짧게 제시하라.
6. 마지막에 `일반 코드 책임 / Agent 책임 / runtime에만 둘 정보 / 기존 DB에 최종 저장할 정보 / 이번에 추가하지 않을 구조`를 표로 정리하라. 현재 frozen schema로 표현할 수 없는 영속 사실이 실제로 확인될 때만 정확한 위치와 이유를 보고하라.
7. 사용자에게 다시 물어야 할 사항은 공개 자료로 결정할 수 없고 다음 실험을 실제로 갈라놓는 선택만 남겨라. 자료에서 확인 가능한 사실이나 이미 승인된 문장·표 행 근거 단위를 다시 질문하지 말라.

## 5. 권한과 제한

이번 요청은 읽기 전용 검토다. 코드·정식 문서·DB·migration·metadata·fixture·의존성·Issue·branch·PR을 변경하거나 모델 호출과 데이터 적재를 수행하지 말라. 공개되지 않은 API 키, 기사 전문, 모델 원응답과 추론 기록을 요구하거나 외부 서비스에 옮기지 말라.

웹과 공개 GitHub는 읽기 전용으로 참고할 수 있다. 외부 근거를 사용하면 공식 문서·논문·공개 구현을 구분하고 직접 URL과 확인한 버전·commit을 적어라. 다른 언어·모델·과제의 결과를 이번 한국어 Qwen 성능으로 바꾸어 설명하지 말고, 적용되지 않는 차이와 반대 근거를 함께 제시하라.

우리가 원하는 답을 맞히는 것보다, 이 결과가 원문 보존 문구의 효과를 과장했거나 다음 실험이 잘못 설계됐다면 정확히 멈추게 하는 것이 검토의 목적이다.
